1. 結論

読み手
Web フロントエンドまたはインフラ担当で、フォントの圧縮手法を体系的に知らない人。まだ「フォントは WOFF2 にすれば十分」と考えている段階も想定する。
結論
日本語フォントを 1 ファイルで配信する限り、WOFF2 でも 0.36〜11.6 MB（実測）は避けられない。実測の結果、最良の運用は「頻度上位の数百文字を 1 枚にまとめた共有ベース（層 1）＋ ページ本文の厳密サブセット（層 2）＋ 不足グリフを差分で足す IFT（層 3）」という 3 層構成である。圧縮率を競うのではなく、どのグリフを配るかを選ぶことで、1 ページあたり 110 KiB（層 1 のみ）まで削減しながら、キャッシュ再利用性と欠落グリフ防止の両方を保てる。
頼みたいこと

2. 背景：なぜ CJK フォントは巨大なのか（実測）

Web フォントの大きさは「文字数 × 1 文字あたりの輪郭の複雑さ」でほぼ決まる。日本語・中国語・韓国語（CJK）は 1 文字あたりの輪郭点数がラテン文字の 10 倍以上であり、1 万〜3 万文字規模のグリフを持つ。既存手法（WOFF2）はファイル全体の圧縮率で攻めるが、実測すると WOFF2 でも元ファイルの 40〜55% が残る。残りを減らすには、配るグリフを減らすしかない。

輪郭の形式が圧縮率を決める。実測した TrueType（glyf）outline のフォント 11 種は WOFF2 化で平均 38% まで落ちたのに対し、CFF（charstring）outline の Source Han Sans JP は 70% に留まる。WOFF2 の内容依存変換は glyf / loca / hmtx にしか適用されず、CFF には Brotli の静的辞書による圧縮しか効かないためである（仕様 5.4 章は CFF のデサブルーチン化を推奨し、平均 5〜10% の削減を報告している）。CJK で CFF を選ぶ場合は、WOFF2 化の効果を過大評価しないこと。

3. 現状の圧縮・配信手法と長所・短所

2026 年 11 月時点で実際に使われている手法を 5 系統に整理した。数値欄は本レポートの実測値、記述は W3C 仕様・各社の公式資料・論文に基づく。

手法長所短所根拠
A. 単一ファイル配信
TTF / OTF / WOFF2 をそのまま 1 ファイルで配信		実装が単純。1 リクエストで完結し、全グリフが揃うので欠落グリフも組版崩れも起きない日本語で 0.7〜8.1 MB（実測）。1 ページで全量をダウンロードする。CLS / FOIT の主因。CDN 帯域も無駄実測 §2
B. WOFF2 コンテナ化
Brotli + glyf / loca / hmtx の内容依存変換		内容依存変換と Brotli で概ね 40〜55% 圧縮（実測）。全ブラウザ対応（2018 年に W3C 推奨）圧縮はできても「何を送るか」は減らない。Brotli の静的辞書は英語中心で CJK には効きにくい実測 §2
C. unicode-range スライス分け
静的サブセットを複数ファイルに分割		必要な文字を含むスライスだけ取得。スライスはサイト横断でキャッシュ共有される。動的コンテンツにも対応できるスライスの粒度が粗いと取り違えで無駄取得。CSS が肥大化（実測: 日本語で 116 KB）。文字が境界をまたぐと kerning やルビが壊れる実測 §4・§6
D. ビルド時サブセット
ページ本文から必要な文字だけ抽出		静的ページなら同一ページで理論最小（実測でも最も小さい）。CLS を最小にでき、表示が速いページが動的だと取りこぼしで豆腐化。ページごとにファイルが違うためキャッシュ共有が効かない。全ページのビルドコスト実測 §6
F. バリアブルフォント
可変フォントでウェイト軸を持つ		1 ファイルで複数のウェイトを表現でき、フォントのリクエスト数を抑えられる。CSS からの制御も細かいCJK では可変ファイルのほうが静的より大きい（実測: Noto Sans JP で可変 4.35 MB に対し静的 400 重み 2.29 MB）。1〜2 ウェイトしか使わない場合は静的が有利実測 §3.2
E. 動的サブセット / IFT
DOM 監視、または差分パッチで不足グリフを足す		任意のテキストに対応できる。IFT は元フォントの組版ルールを保ったまま拡張でき、スライス境界の問題がないサーバ側の動的処理が要る（Adobe / Monotype は商用提供）。IFT は 2026-10 時点で CR 段階で、ブラウザ実装は Chromium の実験段階仕様 §3.1・§10

A〜E は排他ではなく併存できる。実務では「B を土台に、C で共有し、D で削り、E で補完」という組み合わせが現実解になる。本レポートの提案（§8）はこの組み合わせを 3 層として明示し、各層の役割と測定値を分けるところまで分解する。

試算 実 IFT パッチではなく「ベース ＋ 当該ページの文字を含むフォント」のサイズ差で差分コストを近似した値。実 IFT はテーブル更新のみを運ぶため、この試算より小さくなる。

ベースは全ページ・全サイトで共通なので一度取得すれば済み、ページごとの差分だけが小さい。通信上の理想は「ベースを共有し、差分だけページごと」という配分である。ベース 500 文字で試算した合計は 135.6 KiB で、共有ベースのみ（110.6 KiB）との差は 25 KiB 程度だった。

6.2 実測から分かったこと

  1. 圧縮率より「何を配るか」が効く。同じ Noto Sans JP でも、1 ファイル配信なら 4.35 MB、共有ベース 500 文字 ＋ 尾部なら 111 KiB（実測）で約 1/40 になる。
  2. Google 方式は 1 ページあたり中央値 509 KiB・43 スライスに及び、グリフ利用率は 18.9% にすぎない。1 スライスに 200 字以上が入り、必要なのは数文字だけなのに数百グリフを同時に取得している。
  3. 頻度上位の少数を 1 つの共有スライスに固めるのが最も効いた。ベース 500 文字は要求数 1 回・キャッシュ共有可・未学習ページでも 161 KiB と安定する。ベースを大きくしすぎると不利になる（3,000 文字では 487 KiB まで膨らむ）。
  4. 厳密サブセットは最小だがキャッシュを壊す。ページごとに違うファイルになるため、同一サイト内の 2 ページ目以降でも同じコストがかかり、セッション合計では方式 C に負ける。
  5. 共起による学習分割は、小さなコーパスでは過適合する。学習ページでは Google 方式を上回るが、未学習ページでは下回った（上の図）。実運用のコーパスは本レポートの 21 ページよりはるかに大きく、MLFont が報告した規模（2020 サイト）であれば結論は変わりうる。
  6. IFT は「ベースは共有、差分だけページごと」という理想的な配分を出す。ただし実装は CR 段階であり、普及までは後付けの代替（ベース ＋ 尾部で全覆盖）が必要になる。

8. 提案：3 層配信「KOTO」の設計

本章の提案は、既存の手法 A〜E を「層」に再編成し、①転送量を最小化し、②キャッシュを共有し、③欠落グリフを起こさないの 3 つを同時に満たすことにある。名前は「KOTO（問う）」— フォントがページの内容に合わせて自分で選ぶ、という意味を込めた。中心となる観測は 1 つです。「必要な文字の厳密集合」だけを送るのではなく、頻度上位の数百文字でほぼ足りる。

8.1 層 1：共有ベーススライス（頻度上位の少数を 1 枚に）

日本語コーパスで出現頻度（トークン頻度）が上位の数百文字だけを 1 枚の WOFF2 にまとめ、全ページ共通の URL で配信する。残りの文字は符号位置の連続区間（尾部 100 分割）に分ける。

  • 効果：実測で 1 ページ中央値 111 KiB（ベース 500 文字）、要求数 1 回。Google 方式の 509 KiB から約 1/5 に縮む。
  • キャッシュ：ベースは全ページ共通なので、一度取得すれば 2 ページ目以降は再取得しない。CDN 側でも同一ファイルが一度だけ取得される。
  • ベースサイズの決め方：ベース 500 → 111 KiB、1,000 → 183 KiB、3,000 → 487 KiB。小さいほど，共有で効く。実運用の推奨は 500〜1,000 文字。
  • 副産物：ベース 1 枚＋尾部 100 枚で文字集合を完全にカバーできるので、どの文字が出ても豆腐化しない（層 3 がなくても安全）。

8.2 層 2：ページ適応型の厳密サブセット（本文のためだけ）

サーバまたは CDN のエッジで HTML を解析し、可視テキストの文字集合から直接サブセットを生成する。層 1 では出なかった文字だけを含む、ページ固有の 1 枚を追加する。

  • 効果：同一ページでは理論最小（§6 の方式 D、中央値 102 KiB）。層 1 で足りている場合は 0 バイトの追加で済む。
  • 代价：ページ固有ファイルはキャッシュ共有できない。層 1 と併用することで、共有できる部分を最大化する。
  • 運用：Cloudflare Worker / プラットフォームの Functions / ビルド時プラグインなど、HTML を生成する場所で一度だけ実行し、woff2 を不変ファイルとして CDN に置く。生成コストは pyftsubset 1 回あたり数百 ms〜数十秒（実測: 日本語フォント 1 種をサブセットして WOFF2 化するのに 10〜115 秒。ただしページ用の小数は数秒）。

8.3 層 3：IFT 差分パッチ（動的テキストの補足）

層 1・2 で配らなかった文字（コメント欄・ユーザー名・JS 生成テキスト）は、IFT の差分パッチで後から足す。差分はベースフォントを辞書に持つ Brotli パッチとして作られ、追加バイトは新規グリフの輪郭にほぼ比例する。

  • 実装：W3C IFT 仕様（2026-10 CR）。Chromium に実験実装があり、tech(incremental) でオプトインできる。
  • 現状の制約：CR 段階のため Firefox / Safari では使えない。非対応ブラウザでは層 1・2 とフォールバック（システムフォント、font-display: swap）で賄う。
  • 代替：IFT を採用しない場合でも、層 1 の尾部に「残り全部」のスライス（方式 D と同じ扱い）を足せば、欠落グリフは起きない。実測ではベース 500 文字の IFT 合計は 135.6 KiB で、ベースのみの 110.6 KiB との差は約 25 KiB だった。

8.4 効果のまとめ（実測と試算を区別する）

層役割転送量キャッシュ根拠
層 1共有ベース 500 文字 ＋ 尾部 100 分割111 KiB（中央値）／要求 1 回全ページ共有実測 §6
層 2ページ本文の厳密サブセット102 KiB（中央値）ページ固有実測 §6
層 3不足グリフの差分（ベース 500 込み）136 KiB差分試算 §6.1

主張は 1 点に絞れる。圧縮率を上げるのではなく「配るグリフを選ぶ」ことで、実測で 1 ページあたり 110 KiB（層 1 のみ）まで落とせる。その上に、ページ固有の最小化（層 2）と動的テキスト 대응（層 3）を足す。層 1 だけなら 1 リクエストで完結し、キャッシュは全ページ・全サイトで共有される。

8.5 この手法が「新しい」点と、既知の先行研究との関係

  • 新しい点：頻度にトークン頻度（文書頻度ではなく）を使う点、ベースを 1 枚にまとめる点、ページ適応型厳密サブセット（層 2）と共有ベース（層 1）を重ね合わせる点、そして実 WOFF2 バイトとキャッシュ再利用性を同じ指標で比較している点。
  • 既知の先行研究：Zipf 層 + 共起 topic による学習型スライス（MLFont, arXiv:2610.24937）、PFE の Patch Subset（2020）、Google Fonts の 124 スライス（2018）。本稿の位置づけは §10.2 に整理した。
  • 本稿の実測が先行研究と食い違う点：本稿の小さなコーパス（21 ページ）では共起学習が過適合し、単純な頻度ベースが勝った。コーパス規模に依存するため、MLFont の 2020 サイト規模では結論が変わりうる。この食い違いは「学習型分割が常に有利とは限らない」という実装者向けの警告として重要である。

9. 実装と検証手順

  1. 現状を測る：DevTools の Network で自サイトのフォント要求数と合計バイトを測る。日本語ページで数百 KiB〜数 MB なら対象とする価値がある。
  2. 層 1 の共有ベースを作る：自分のサイト（または同種の日本語サイト群）の本文からトークン頻度を数え、上位 500〜1,000 文字を 1 枚の WOFF2 にする（pyftsubset --flavor=woff2 --no-hinting）。残り 13,000 文字前后は符号位置の連続区間 100 枚に分ける。unicode-range は各スライスの文字集合から自動生成する。
  3. 層 2 のページ固有サブセットを追加する：Node.js や Python で HTML から本文テキストを抽出し、pyftsubset --text-file=page.txt --flavor=woff2 を実行する。生成物を不変ファイルとして CDN に置く。
  4. 層 3 を検証する：Chrome Canary で tech(incremental) を使い、Chromium の実験実装を実ページで確認する。
  5. 前後で測り直す：本レポートの measure/ スクリプトで同じ指標（1 ページバイト数・要求数・グリフ利用率・セッション合計）を before / after で比較する。

9.1 最小構成の CSS 例

/* 層1: 全ページ共通のベース（頻度上位 500 文字） */
@font-face {

  src: url("/fonts/koto/base-500.woff2") format("woff2");

  font-display: swap;

10. 標準化・今後の論点

論点現状本研究での位置づけ

10.1 共有辞書圧縮の試算

試算 実運用では WOFF2（Brotli 済み）に外部辞書を適用する手段がないため、そのまま使える技術ではない。フォントを sfnt のまま配信し RFC 9842 の圧縮辞書転送（Chrome の dcb/dcz）を使う場合の実現性を見るための上限試算。

結論：CJK フォントでは共有辞書圧縮は効かない。5 種の CJK フォントの輪郭から 1 MiB の Zstandard 辞書を学習し、held-out の 3 フォントで比較したところ、圧縮率は 0〜0.4% の変化に留まった。理由は、漢字の輪郭がフォント間でバイト単位で共通化されていないこと（同じ漢字でも設計ごとに輪郭が 다르る）にある。したがって「圧縮辞書を全フォントで共有する」方向への投資は CJK では成果が望みにくく、配るグリフを選ぶ方向に投資すべきである。

10.2 先行研究（MLFont）との差分

  • 共通点：文字頻度を使い、静的スライスで配信量を減らす。本稿の層 1（頻度上位を 1 枚にまとめる）は MLFont の Tier-1 に相当する。
  • 違い①：MLFont は Headless Chrome とネットワークシミュレータでの評価が中心。本稿は 実 WOFF2 バイト数と実ページの文字集合で比較し、キャッシュ再利用性を数値で示している。
  • 違い②：MLFont はスライス最適化に焦点を置く。本稿は共有ベース（層 1）・ページ固有の厳密サブセット（層 2）・IFT 差分（層 3）の 3 層構成を全体として提案する。MLFont の中心である共起 topic 分割は、本稿の実測では小さなコーパスで過適合した（§6 の図）。
  • 違い③：MLFont は Latin も対象に含む。本稿は日本語 Web に対象を絞り、CJK 固有の「文字数 × 輪郭バイト」という制約に集中している。
  • 違い④：MLFont はネットワークシミュレータと Headless Chrome でレイテンシを評価する。本稿は実 WOFF2 バイト数・要求数・グリフ利用率・キャッシュ再利用率で比較し、さらに共有辞書圧縮が CJK では効かないこと（§10.1）と、CFF フォントは WOFF2 で圧縮されにくいこと（§2）を実測した。

付録 C：用語

グリフ
文字を画面上に描くための図形データ。日本語フォント 1 種で 8,000〜65,000 個。
サブセット化
フォントから必要なグリフだけを取り出す操作。
unicode-range
@font-face で「このファイルはどの文字用か」を宣言する CSS 記述子。ブラウザは必要な面だけ取得する。
スライス
unicode-range 用に分割したフォントファイル 1 枚。
IFT
Incremental Font Transfer。必要な部分だけを後から差分送信してフォントを拡張する W3C 仕様（CR Draft）。
Brotli 辞書
RFC 7932 の静的辞書（英語テキスト中心）。RFC 9842 の圧縮辞書転送はサイト間で共有する辞書を配信する仕組み。
グリフ利用率
取得したグリフ数に対する、実際に表示された文字数の割合。取り違えが小さいほど高い。
FOIT / FOUT
フォント読み込み中に文字が透明なまま何も見えない現象 / フォールバックで一瞬見える現象。

付録 D：English summary（Plamo 3 Translate による日本語→英語翻訳）

Japanese web fonts have a large number of glyphs and large file sizes, which cause delays in initial display and increased communication volume. In this study, we quantitatively compared the effectiveness of each compression and distribution method based on 12 measured CJK fonts, actual pages from 44 sites, Google's actual font slicing, and W3C specifications and research papers. The results showed that a three-layer configuration—a shared-based slice that consolidates the top-most few hundred characters into a single page, a strict subset that exactly matches the page body, and an incremental font transfer (IFT) that adds missing glyphs via differences—can reduce transfer volume to approximately 110 KiB per page while maintaining cache reuse and no missing glyphs. This demonstrates that even when generating strict subsets per page for nearly the same number of bytes, the former allows the cache to be shared across all pages and sites. Furthermore, we measured that the CJK outline only improves by 0–0.4% in compression ratio when using the shared compression dictionary, and that variable fonts are approximately twice the size of static instances. This report includes the measurement procedure, reproduction scripts, and materials summarizing the measured values. 日本語の要約（§1 結論欄に対応）を Plamo 3 Translate 0.8B (Q4_K_M) で英語に翻訳したもの
