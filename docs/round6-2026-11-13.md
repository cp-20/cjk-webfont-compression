## Round 6, item 2 — Per-weight usage: browser computed-style second pass

### Method and reproducibility

`measure/weight_usage_browser.py` uses Playwright with system Chromium
156.0.8078.79 at 1440×1000. It navigated live corpus URLs, respected the corpus
robots helper, waited for `load`, another 3 seconds, and `document.fonts.ready`
(capped at 10 seconds). The environment proxy certificate was trusted by its
specific SPKI pin; general certificate verification was not disabled.

The sample is 12 successful corpus pages, four each in ja/zh/ko. Selection
prioritised encyclopedia/news/government/literature or tech/blog sources, then
fell back to corpus order. This is a purposive check, not a representative
resampling of the entire corpus. Skipped URLs and reasons are in the JSON.

A DOM TreeWalker records each visible text node's text, Unicode code-point
count excluding whitespace, `getComputedStyle(parent).fontWeight`, font
family, and membership in the estimator's text scope. Counts weight text
runs by characters, not by node or page. Visibility requires a positive
Range rectangle and excludes hidden visibility, ancestor display:none,
content-visibility:hidden and opacity:0. Text below the viewport is included.

Two browser views are reported: the full rendered body and the same
main/article/body scope and tag/role/class exclusions as `weight_usage.py`.
The original estimator is also rerun on the exact main-document response
bytes fetched for each browser page, avoiding a second independent fetch.
Its result still includes text it cannot recognise as CSS-hidden; this is
part of the estimator's approximation. DOM changes made by JavaScript are
only reflected in the browser view.

Raw data: `measure/out/weight_usage_browser.json` (per-run records, per-page
and per-language counts, same-response estimator counts, failed requests,
selection and browser provenance). Reproduce with Playwright installed in
the existing virtualenv and `/usr/bin/chromium`, then run
`.venv/bin/python measure/weight_usage_browser.py`. No dependency manifest
or production code was changed.

### Interpretation and limits

The comparable browser scope puts other weights at **0.5390%**,
+0.4090 percentage points versus the old 0.13% full-corpus
estimate. The full-body figure is 0.5319%.
These differences combine sampling, changing live pages and rendering;
the same-response estimator row isolates the comparison more closely than
the historical reference alone. Character pooling gives long encyclopedia
and literature pages much more influence than short news/government pages.
The language and per-page rows are therefore essential to the verdict.

**Verdict: the blanket “instance only {400,700}” guidance does not survive.**
Those weights still cover **99.4610%** of pooled scoped characters, so they
remain a useful starting pair for sites whose actual styles ask for them.
But the round-4 claim of ≥99.8% in *each language* is contradicted by this
sample: coverage is 99.9553% in ja, **97.8305% in zh**, and **96.3848% in ko**.
The same-response estimator reports **zero** characters outside 400/700,
whereas the browser finds **3,244**. Its simplified cascade misses real
300/500/600/900 usage; the discrepancy is not just the historical corpus
having a different mix of pages.

At page level, other weights comprise **13.8288%** of People's Daily,
**51.8658%** of Korea.kr, and **10.8231%** of Brunch's scoped text. These are
not rounding errors for those sites. The pooled result is dominated by
Japanese text (83.64% of scoped characters), especially the long Aozora
novel. Do not use that pooled percentage to discard weights from a real
site. Instance the weights actually requested by that site's computed
styles; keep {400,700} when that audit supports it. The earlier font-size
measurements still stand, but their two-weight demand premise no longer
supports an unconditional delivery recommendation. This pass does not
reprice a specific site's multi-weight static versus variable delivery.

**Verification and limits.** The browser walker passed an assert-based
fixture covering inheritance, bold, a descendant selector using the `font`
shorthand at 500, inline 300, display:none, and navigation exclusion.
Assertions also check ≥10 pages, all three languages with ≥3 pages each,
and conservation of per-run versus per-page character totals. The final
run has four pages per language; Python compilation and independent JSON
aggregation checks passed. No stylesheet/font transport failures were
recorded on accepted pages (the log does not audit every HTTP subresource
status). Kantei returned 404; YNA did not supply 100 scoped characters, so
both were skipped and replaced in corpus order.

Computed CSS weight is the browser-resolved requested weight, **not proof
of which physical font face/glyph was selected**: fallback fonts, synthetic
bold, and a font's available weight range can change the actual outlines.
This pass measures CSS demand, which is the relevant input to choosing
instances. It does not count generated pseudo-element text, shadow DOM,
iframes or canvas, test occlusion or individual glyph clipping, or scroll
to trigger lazy content. Text nodes with any positive rectangle contribute
the whole non-whitespace run; this is a visibility approximation. Results
are for one desktop viewport and live-page snapshot, not all responsive
states, interactions, or the entire corpus. They suffice to reject a
universal two-weight rule, not to establish a replacement universal set.

## Item 3: protected mode on SC/KR variable fonts

**The JP pattern broadly carries over to these SC/KR fonts: exempting about
1–1.5% of glyphs caps the measured interpolation error for a small size
increase. The exact +0.22% price does not carry over: SC costs +0.19%,
KR +0.40%.** At grid 8, both fonts' worst sampled error falls from 138 to
16 font units. Neither protected file beats static instancing: SC is
15.53% larger than its Arm A {400,700} bundle, and KR is 13.59% larger.
For one or two weights, the recommendation remains to instance per weight;
protected mode remains an experimental option when more weights are needed.
This completes round 5 §6 item 3 only; nothing was merged or published.

### Delivery size: protection versus static instances

All sizes are WOFF2 bytes. Arm A uses the same CLI helper as round 5:
instance the original font at each weight, drop vertical metrics, run
`process_font` at grid 8 with canonicalisation off, then WOFF2-encode.
The {400} total is the helper's 400 entry; {400,700} sums the two files.
These full-font delivery sizes are distinct from round 5's static demo
subset/grid-reference sizes.

| Measurement | Noto Sans SC | Noto Sans KR |
|---|---:|---:|
| Stock variable WOFF2 | 7,782,072 B | 3,908,716 B |
| Unprotected variable WOFF2 | 7,101,732 B | 3,610,788 B |
| **Protected variable WOFF2** | **7,115,560 B** | **3,625,092 B** |
| Protection cost vs unprotected | +13,828 B (+0.19%) | +14,304 B (+0.40%) |
| Protected vs stock | −8.56% | −7.26% |
| Arm A {400} total | 3,026,468 B | 1,573,548 B |
| Arm A {700} (for the sum below) | 3,132,540 B | 1,617,704 B |
| Arm A {400,700} total | 6,159,008 B | 3,191,252 B |
| Protected vs Arm A {400} | +4,089,092 B (+135.11%) | +2,051,544 B (+130.38%) |
| Protected vs Arm A {400,700} | +956,552 B (+15.53%) | +433,840 B (+13.59%) |

Round 5's JP reference was +8,744 B (+0.22%) over unprotected. SC is close
in percentage terms; KR's +0.40% is about 1.8 times JP's premium, though
still small in absolute delivery cost. Across these three Noto Sans fonts,
the exemption tail stays small (1.04–1.52%) and protection reaches the same
16-unit sampled bound. That supports the qualitative pattern, not a fixed
1.3% exemption rate or a universal +0.22% size prediction for other fonts.
The static {400,700} bundle wins in all three scripts. These measurements
do not establish a break-even point for three or more weights.

### 日本語まとめ

ラウンド5の「少数のグリフを量子化対象から外すことで、小さなサイズ増で
補間誤差を抑えられる」という傾向は、今回の Noto Sans SC/KR でも確認できた。
格子幅8で、SC は322個／31,032個（1.04%）、KR は379個／24,957個（1.52%）を
免除し、測定した全ウェイト（100・500・900）で最大誤差を16単位以下に抑えた。
最悪値は両方とも138→16、点数不一致は保護前後とも0だった。

保護後の WOFF2 は SC が7,115,560 B（未保護比 +13,828 B、+0.19%）、
KR が3,625,092 B（+14,304 B、+0.40%）。JP の約1.3%の尾部という規模感は
共通するが、+0.22%というサイズ増がそのまま一般化するわけではなく、
特に KR は約1.8倍の増加率だった。

Arm A の {400} 合計は SC 3,026,468 B／KR 1,573,548 B、{400,700} 合計は
SC 6,159,008 B／KR 3,191,252 B。保護後の可変フォントは2ウェイト合計より
