# Round 4 (2026-11-13): the Korean corpus grows teeth, real pages render in exactly two weights, the report rebuilds from public data, and the gvar-aware quantiser gets a priced verdict

## What this round did, in one paragraph

Round 3's cross-script claims rested on 7 Chinese and 4 Korean pages; this
round extends the corpus behind `corpus_stats.json` to **14 usable Chinese
and 15 usable Korean pages** (70 records in total) and re-runs the combined
study: the conclusions do not move (GLC's median gain on exact subsets: zh
18.2 %, ko 16.0 %; §1). A new measurement prices the demand side of variable
fonts: across 56 corpus pages and ~1.03 M rendered characters, **94.7 % of
text renders at wght 400 and 5.2 % at 700 — every other weight combined is
0.13 %** — and recomputing round 3's Arm A prices from the surviving
artifacts shows what each weight costs (§2). The delivery report now builds
from the committed `corpus_stats.json` instead of the non-redistributed
`corpus.json`, verified to reproduce every KPI from a clean checkout (§3).
Finally, the gvar-aware quantiser design study (`docs/gvar-aware-quantiser-
design.md`) is backed by two prototypes: the IUP error amplification is
concentrated in **1.3 % of glyphs**, and exempting that tail caps the worst
error at 16 units for **+0.21 %** file size — yet the protected single file
(≈3.99 MB) still loses to the two GLC instances (3.57 MB) that §2 shows are
all real pages need, so the full quantiser is **not** worth implementing
now (§4). Demo zh/ko live preview (backlog item 5) did not fit this round's
sequential-CPU budget and heads the round-5 list (§6).

## 2. Which weights are worth instancing: a two-weight web

Round 3 priced every weight (Arm A) but never measured demand.
`measure/weight_usage.py` re-fetches each corpus page and estimates, per
visible character, the weight it renders at — a deliberately simple
cascade model (UA defaults for `b`/`strong`/headings, inline styles, and
`<style>` rules with simple selectors; same text scope as the corpus
extraction; the model and its approximations are documented in the
script). 56 of 60 usable pages measured (4 fetch failures, listed in the
JSON), 1,032,332 non-space characters:

| weight | ja | zh | ko | all |
|---|---|---|---|---|
| 400 | 94.85 % | 95.35 % | 93.41 % | **94.66 %** |
| 700 | 4.95 % | 4.65 % | 6.58 % | **5.21 %** |
| 500 | — | 0.00 % | — | 0.00 % |
| 600 | 0.20 % | — | — | 0.13 % |
| 900 | — | — | 0.01 % | 0.00 % |
| 100/200/300/800 | 0 | 0 | 0 | 0 |

`measure/weight_cost.py` recomputed the supply side from round 3's
surviving `measure/out/vf/` artifacts (the round-3 `variable_glc.json`
itself did not survive; every number below is re-measured, and both of
round 3's headlines reproduce: static GLC gain at 400 = **23.8 %**, VF-safe
single file **−8.6 %**):

| Arm A (instance → GLC g8), full file | bytes |
|---|---|
| {400} | 1,755,620 |
| {400,700} | 3,566,128 |
| {400,500,700} | 5,358,272 |
| all nine weights | 15,935,516 |

Per-page subsets (Japanese pages, median) cost almost the same at every
weight — 400: 61,472 B, 500: 62,248 B, 700: 63,388 B — because subset cost
is driven by the character set, not the weight. So in the subset model
each additional weight costs ≈ another full subset per page (+~62 KB);
in the full-instance model each costs ≈ 1.7–1.9 MB once, cached
site-wide.

**The practical guidance**: instance **{400, 700}**. Together they cover
≥ 99.8 % of rendered characters in all three languages; characters at
other weights are a rounding error (500 appears in 7 of a million
characters). A third weight buys ≤ 0.13 % coverage for +1.79 MB
(full-instance) or +~62 KB per page (subset) — worth it only for a site
whose design system demonstrably uses it (e.g. 500 for UI text), and the
measurement to check is this one, run on the site's own pages. Light and
black weights (100–300, 800, 900) should be served, if at all, from the
variable font or not at all — never as dedicated instances. Caveats:
shares are character-weighted (a bold headline is few characters but
still needs the 700 font present — which {400,700} provides); the
cascade model is an approximation (documented in the script; its one
measured failure mode — chained bare-tag selectors applying page-wide —
was found on Wikipedia and fenced off); 4 pages failed to fetch and are
listed in `weight_usage.json`.

## 4. The gvar-aware quantiser: error solved on paper, size still loses

Full study: `docs/gvar-aware-quantiser-design.md`. Round 3 showed direct
VF quantisation amplifies worst-case error 4 → 138 units while saving
only −8.6 %. The study derives the mechanism (IUP interpolation ratios
are computed from the default geometry; near-coincident referenced
points make the ratio ill-conditioned, so a bounded rounding becomes an
unbounded movement error), states a per-glyph certificate under which
independent rounding provably stays within 2g (movement spread ≤
referenced spacing, `D ≤ s`), and designs the mitigations for glyphs
that fail it (joint pair rounding, delta promotion, exemption). Two
prototypes on round 3's artifacts ground it:

- **Amplification is a tail phenomenon** (`measure/iup_amplification.py`).
  Per-glyph max error of the VF-safe font over all 17,932 simple glyphs:
  at the default (wght **100** — this font's fvar default; round 3's "4
  units" is at 100) every glyph is ≤ 4; at wght 900 the median glyph is
  still 4, but 231 glyphs (1.3 %) exceed 16 and the worst is 138 —
  round 3's headline reproduced exactly, glyph for glyph attributable
  (worst: `uni318E`). Amplification ratio err900/err100: median 1.0×,
  p90 1.0×, p99 12.75×.
- **Protection is cheap** (`measure/iup_mitigation_probe.py`).
  Exempting the 231 tail glyphs from quantisation (mitigation M3, the
  crudest) costs **+8,540 B (+0.21 %)** and caps the wght-900 max error
  at **16** (wght 400: 54 → 9). 80 glyphs remain in the (8, 16] band —
  the empirical target g = 8 needs M1/M2 or a lower threshold, all
  affordable.

**Verdict: do not implement the full quantiser now.** The error half of
round 3's objection is removable for ~0.2 %; the size half is not: the
protected single file is ≈ 3.99 MB against Arm A's {400,700} total of
3,566,128 B — and §2 shows two weights are what real pages use. The
route wins only for ≥ 3-weight delivery (vs 5,358,272 B) or fonts with a
smaller gvar share. A scoped-down "protected mode" for
`--quantize-variable` (measure tail → exempt → verify, one extra
instancing pass) is the round-5 candidate; it makes the experimental
flag honest without the joint optimiser.

## 6. What is next

1. **Demo zh/ko live preview** (this round's item 5, deferred on CPU
   budget, not on merit): SC/KR subset WOFF2 assets per grid in the
   round-3 pattern (`measure/build_demo_assets.py` + a language switch
   on the ε preview), so Chinese/Korean text can be typed and rendered
   live like Japanese.
2. **`--quantize-variable` protected mode**: implement M3-style
   exemption in `tools/glc.py` (build → instance at peaks → measure tail
   → exempt → rebuild → verify ≤ 2g), labelled with the measured
   numbers from §4; the full joint quantiser only if a ≥ 3-weight use
   case shows up.
3. **Per-weight usage, second pass**: the weight estimator's cascade is
   deliberately simple; if the {400,700} guidance is ever load-bearing
   for a real site, re-check with a headless-browser computed-style
   pass on a page subset.
4. Corpus: the Korean base-500/anchor ceiling (1,889 distinct chars)
   and the still-missing Naver/Daum are properties of the accessible
   web from this network, not of the method; revisit only if a
   materially different source class (e.g. Korean government PDFs'
   text, book corpora) is added.
