## Fetch manifest fixes

Based on main `ac3a761` (round 7). The two fetch failures were independent:

- **Source Han subset:** the manifest URL points to Adobe's `2.005R/17_SourceHanSansJP.zip`, while its `sha256`, `bytes`, and `local_path` describe `SubsetOTF/JP/SourceHanSansJP-Regular.otf` inside that ZIP. `fetch_fonts()` ignored the existing `source_archive_member` field and saved/hashed the entire ZIP as an OTF. The manifest checksum was correct; no checksum or manifest metadata was weakened or changed.
- **Null sources:** `fetch_fonts()` passed `None` to the downloader when an asset was absent (or `--force` was used), aborting the fetch. Despite the round-7 description as “derived”, the actual null-source entries on this baseline are `noto-sans-cjk-jp` and `ipaex-gothic`, both `source_kind: local_system`; neither provides a derivation recipe.

The fetcher now downloads archive-backed entries to a temporary directory, extracts only the manifest's named member, and applies the existing SHA-256 comparison to the extracted font. Direct downloads retain their existing behavior. Entries with `source_url: null` are skipped with an explicit warning identifying the asset and explaining that it must be supplied separately. Existing local assets still follow the normal non-force skip behavior.

The initial run found the checkout lacked `origin/gh-pages`; after fetching that existing remote branch, the unchanged Pages integration test passed. The new offline regression test covers named ZIP-member extraction, direct downloads, continuation past null sources before/between downloads, force mode, and continued reporting of deliberately incorrect expected checksums.

Scope: font fetching only; model download and llama.cpp build were not needed or run. Null-source assets remain separately supplied local assets; they are not synthesized. Existing checksum-mismatch reporting behavior is retained.
